# Give categories an identity, not a name

The app should add the trade trees as **one global, keyed category tree per trade** (`category_nodes`) and give every common-list item **one primary node**. Shop items should **not copy that node**. Each item works out its node when it is read: shop override first, then the common-list item's node, then the node its shop category is mapped to, then a name rule, then `<trade>/other`. A hardware shop that picks "Ball valve 20 mm" then sees it under Water & plumbing › Valves in its own list and on the bill, and the customer sees it in the same place in the online store. If the platform later moves the item, every shop follows, unless the shop moved the item itself. This works the way master photos already do. Today almost none of this happens. The common list's category is a **free-text string**. It reaches the shop **once, by text, when the item is picked**. Later edits reach shops only for **GST and HSN, matched by item name**. The online store ignores the shop's category rows entirely and groups by a hard-coded grocery aisle for 71 items and by category strings sorted A to Z for everything else. The fix is mostly plumbing. The app already has a per-shop `Category` table with parents, hiding and merges, and it already stores the `Product.MasterItemId` link. It needs a stable node key on the common-list item, live resolution, one small shop-settings table, and a store payload that carries the tree. That relationship layer takes about **10–13 developer days plus 3–4 days of mapping content**. It sits underneath the menu UI already planned, and it should land before the per-trade menus, not after them.

## Today the category is a label copied once and then forgotten

Five links make up the chain. Today each one is joined by text or not joined at all. `MasterItem` is a flat, platform-owned row with a free-text `Category` of up to 60 characters. It has no category id, no parent and no attribute fields, and no category table exists for it to point to ([MasterItems.cs:14-54](backend/src/GroceryKhata.Api/Catalogue/MasterItems.cs); [AppDbContext.Catalogue.cs:29-41](backend/src/GroceryKhata.Api/Persistence/AppDbContext.Catalogue.cs)). The seven master CSVs hold **3,940 rows in 120 category strings**: beauty 1,017/13, clothes 204/20, electrical 258/18, hardware 319/14, kirana 958/18, medical 847/24 and paint 337/13 ([Catalogue/Data](backend/src/GroceryKhata.Api/Catalogue/Data/)). Only clothes has a second level, and only as a text convention: "Women · Sarees". The one real tree in the code is the kirana `Aisles` list: 4 sections and 16 aisles, hard-coded in C#. It is attached to the 71 `CatalogueItem` rows, not to `MasterItem`, and it assigns aisles by **id range** ([CommonCatalogue.cs:32-58, 118-157](backend/src/GroceryKhata.Api/Catalogue/CommonCatalogue.cs)).

The shop side is better built than it is used. `Category` is a tenant-owned table protected by RLS. It has a normalised unique name, one optional parent level, sort order, an active flag, merges that keep a pointer, and GST, HSN and unit defaults ([Categories.cs:9-45](backend/src/GroceryKhata.Api/Catalogue/Categories.cs)). When a shopkeeper picks from the common list, `AddToShopAsync` copies the master's category **string** onto each new product. `Categories.LinkAsync` then finds or creates a shop category with that name, always as a top-level row ([MasterItems.cs:337-360](backend/src/GroceryKhata.Api/Catalogue/MasterItems.cs); [Categories.cs:83-129](backend/src/GroceryKhata.Api/Catalogue/Categories.cs)). The flattening is visible in clothes: a pick creates a single shop category literally named "Men · Shirts and T-shirts", even though `ParentId` exists. Nothing records which master category a shop category came from. `MasterItemId` is saved on the product, but the update check ignores it. `CompareAsync` matches items **by name** and compares **only GST and HSN**, so a renamed item drops out of updates, and a master re-grouping never reaches any shop ([MasterItems.cs:429-449, 533-546](backend/src/GroceryKhata.Api/Catalogue/MasterItems.cs)). Rows added by `SeedListsAsync` get no `CreatedAt`, while "new items" means `CreatedAt` within 30 days. Existing shops were therefore **never told about the new electrical list or the 65 new beauty items** ([MasterItems.cs:234-242, 445-447](backend/src/GroceryKhata.Api/Catalogue/MasterItems.cs)).

The customer store bypasses the shop's categories completely. `GET /api/v1/store/{slug}` returns every active product priced above zero. It sends only the category string: no category id, no parent, no order ([StoreEndpoints.cs:20-22, 88-91](backend/src/GroceryKhata.Api/Planner/StoreEndpoints.cs)). The frontend groups an item by aisle if its catalogue id falls in the hard-coded ranges, and otherwise under a chip named after its category string. Those chips are sorted A to Z ([StoreApp.tsx:301-312](frontend/src/screens/store/StoreApp.tsx); [itemArt.ts:64-72](frontend/src/lib/itemArt.ts)). The results are odd. In one kirana store, the same kind of item can land in an aisle or in a Hindi category chip, depending on how its name is spelled. A category the shopkeeper hid still shows online, and the order the shopkeeper set is ignored. Only the shop's primary `Type` reaches the store, so a kirana shop with a beauty side shows its beauty goods in the grocery layout, which has no filter drawer ([StoreEndpoints.cs:10-11](backend/src/GroceryKhata.Api/Planner/StoreEndpoints.cs); [StoreApp.tsx:298, 387](frontend/src/screens/store/StoreApp.tsx)). A search for `CategoryMenu|TreeKey|CategoryNode|tradeTree` across backend and frontend source finds nothing, so none of the trees in the earlier menu reports exist in code yet.

## The marketplaces already settled the shape: one standard category, many shelves

Every large catalogue platform separates three things that the app currently blurs together. The first is a **shared product record**: Amazon's ASIN and Flipkart's FSN. The second is the **seller's own offer**, which points at it: SKU, price, stock and delivery time. A seller whose product already exists "matches" or "latches" to it and sets only offer fields ([Amazon India](https://sell.amazon.in/sell-online/list-your-products); [Flipkart LM API glossary](https://seller.flipkart.com/api-docs/glossary.html); [Fynd: Flipkart latching](https://documentation.fynd.com/commerce/docs/openapi/listings-management/flipkart/existing-products)). The shared page is never edited into a different product by a seller ([Amazon ASIN policy](https://sellercentral.amazon.com/help/hub/reference/external/G201844590)). That matches the app's common list and `Product.MasterItemId` exactly, and "add from common list" is the app's version of latching. The third separation is between the **standard category**, which drives tax and channel mapping, and the **store navigation** layered on top. Shopify gives each product exactly one standard taxonomy category, and lets the merchant build many collections over it, including rule-based ones such as "this category and all its descendants" ([Shopify changelog](https://shopify.dev/changelog/introducing-productcategoryidwithdescendants-in-collectionrulecolumn-for-smart-collections)). Google likewise splits the fixed `google_product_category` from the merchant's own `product_type` ([Google Merchant Center](https://support.google.com/merchants/answer/6324406?hl=en)). Both taxonomies use stable ids. Shopify releases its taxonomy in dated versions and **archives** categories rather than deleting them ([Shopify/product-taxonomy](https://github.com/Shopify/product-taxonomy)).

Two more patterns carry over. Meesho and ONDC attach an **attribute template to each category**: size chart for fashion, statutory blocks for packaged goods ([Meesho QC](https://supplier.meesho.com/learning-hub/lessons/how-to-find-and-fix-qc-errors); [ONDC attribute sheet](https://docs.google.com/spreadsheets/d/1APAvavF_BNbTA89benAlGtv0GuFvpn2b6XXi4lSdTTw/export?format=pdf)). That is the model for "sq mm on wire, shade on lipstick, purity on gold". Variant families share their parent's category and variation theme, and Amazon children reportedly come loose when their category drifts from the parent's ([Google item_group_id](https://support.google.com/merchants/answer/6324507); [Amazon seller forum](https://sellercentral.amazon.co.uk/seller-forums/discussions/t/93ea070a-7950-4026-9aef-03cb06bf5af1)). Among Indian billing apps, none documented shop-level overrides on top of a shared master list. Vyapar has shops create their own items and then add chosen ones to "My Online Store" ([Vyapar guide](https://vyaparapp.in/guides/how-to-create-an-online-store-in-vyapar)), and Khatabook shut its storefront in 2021 ([Inc42](https://inc42.com/buzz/khatabook-pulls-the-plug-on-digital-shopfront-platform-mystore-within-a-year-of-its-launch)). The design below is therefore borrowed from the marketplaces, not copied from a direct competitor. The gap is also an opening.

## Five links, one resolution rule

### Global nodes with stable keys, three levels deep

Add a global table `category_nodes`. Like `master_items`, it has no RLS and rows are never deleted. Store it as an adjacency list, with one level per row: **department (rail) → group (tile) → type (chip)**. Each node carries `Id`, a `Key` that is unique, ASCII and never reused (for example `hardware/water/valves` or `clothes/women/bottoms/jeans`), `Trade`, `ParentId`, `Level` (CHECK ≤ 3), `NameEn`, `NameHi`, `NameGu`, `Icon`, `SortOrder`, `IsActive` and `MergedIntoId`. Three extra fields solve the cases the earlier reports raised. `TypeKey` lets "jeans" under Men, Women, Girls and Boys count as one type for search and reports. `LinkToId` makes a shortcut tile, so medical's Diabetes can show under both Chronic care and Ayurveda without a full multi-parent graph. `Aliases` holds Hinglish and Devanagari words plus the **old category strings**, which is what makes migration mechanical. **The key is an identity, not a path.** If a node moves, only `ParentId` changes, so CSVs, shop overrides and cached phones keep working. Each trade's tree has 40–150 nodes and the whole set is under about 1,500, so every trade's tree can be held in memory the way `Aisles.All` is today. PostgreSQL ltree would add an extension and test-container setup for no gain at this size ([Neon ltree docs](https://neon.com/docs/extensions/ltree); [DEV comparison](https://dev.to/dowerdev/implementing-hierarchical-data-structures-in-postgresql-ltree-vs-adjacency-list-vs-closure-table-2jpb)). Seed the table from an embedded `category-nodes.csv` per trade, using the same "only add, never overwrite an admin edit" rule as `SeedListsAsync`. Phase 1 then needs no admin editor, and one can be added later without any data change. Every trade also gets a reserved `<trade>/other` node, so "unmapped" is never null.

### Common-list item: one home, a few shortcuts, attributes for the rest

`MasterItem` gains `NodeId` (the one primary home), `ExtraNodeIds int[]` (at most about three, in the same trade, for "also shown under") and `Attrs jsonb`. `Attrs` is checked against a per-trade attribute registry in C#, and unknown keys are rejected on admin save and CSV import. Every master CSV gets `node` and `attrs` columns. The rule for choosing between a tree level and an attribute: **a node is a shelf the counter walks to, with its own size scale. An attribute is a property that cuts across many shelves or narrows within one.** That rule produces different answers for different trades, as the table shows.

| Trade | Tree (rail → tile → chip) | Attribute, not a node | Why |
|---|---|---|---|
| Kirana | 7 departments → about 20 tiles (dal, masala, dry fruits split out of merged Hindi strings) → sparse chips (तूर · मूंग · चना) | Pack size, brand, veg mark | Replaces both the 16 hard-coded aisles and the 18 merged strings with one vocabulary |
| Hardware | **Water & plumbing** (pipes, fittings, valves, taps & bathroom, drainage & traps, solvent & Teflon, tanks & pumps) · Fasteners · Door & furniture · Tools · Adhesives & sealants · Safety · Building material; pipe type (CPVC/UPVC/PVC/GI) as chips | Size in mm and inch, material, finish, SDR, unit of sale, hot/cold | Water is its own department, not a 71-item bucket mixed with glue |
| Paint | Interior · Exterior · Enamel & wood · Primer & putty · Waterproofing · Tools & thinner | Brand, range tier, finish, pack; shade stays on the bill line | The existing tint sheet keeps working |
| Electrical | 9 rail entries over the **18 CSV groups** | sq mm, amps, poles, watts, light colour, sweep, coil length, colour | All numeric; parsed from names at import, because the 258 names follow one pattern |
| Beauty | Areas: Face, Body, Hair, Makeup, Lip & nail, Shaving & beard, Baby bath & body; **Salon use** as its own department | **`for` = women/men/kids/baby/unisex (multi)** drives the Women · Men · Kids & baby · Salon switch; `use` = retail/salon; skin type, concern, shade | About 145 items are unisex. Making Women and Men tree levels would duplicate them; one facet value per item drives the switch |
| Clothes | Women · Men · Kids Girls · Kids Boys · Baby girl · Baby boy · School · Winter · Accessories · Fabric → group → type, with shared `TypeKey` | **Age band and size are `Product.Size`**, plus colour, fit, fabric, occasion | Gender and age change the size scale and the shelf, so here they are tree levels, the opposite of beauty |

Beauty and clothes look alike on the screen, since both have a Women/Men/Kids switch, but they need opposite storage. A shampoo is sold to everyone from one shelf, so "for" is an attribute and the switch is a filter. Women's and girls' jeans sit on different shelves with different size ladders, so in clothes the department is the tree. The beauty counts behind this are rough regex counts. Of 53 names containing a men word, 40 are already in Men's grooming and 13 are elsewhere, such as "Nivea Men Deodorant". The Women/Men/Kids/Salon split is the owner's own request; no source confirmed it as Indian counter practice ([beauty-master.csv](backend/src/GroceryKhata.Api/Catalogue/Data/beauty-master.csv)).

### Shop item: inherit live, never copy

Keep `Product.MasterItemId` as the link, and add a nullable `Product.NodeId` as an explicit shop override, where null means "follow the common list". Add `Category.NodeId` to the existing shop table, meaning "items in my category X belong under node Y". Then resolve each product's node when it is read, with one pure function that has a C# twin and a TypeScript twin:

> **effective node = `Product.NodeId` → `MasterItem.NodeId` → shop `Category.NodeId` → name keyword rule → `<trade>/other`**, following `MergedIntoId` at every step.

This is already how photos work. The store sends `p.ImageAt ?? p.MasterItem.ImageAt`, so the master link is joined on every read already ([StoreEndpoints.cs:93-95](backend/src/GroceryKhata.Api/Planner/StoreEndpoints.cs)). Nodes ride the same join. Because the node is never copied onto the product, a platform re-grouping (such as splitting "Pipes and fittings" into seven water tiles) reaches every linked product in every shop **at once, with no fan-out job**. Free-text `Product.Category` stays as the shop's own reporting label. About 20 screens, including the stock statement, P&L and stock health, group by it, and replacing it in v1 would risk regressions on all of them. The node is a second, browse-only dimension.

Picking changes very little. `POST /products/from-master` needs nothing new for inheritance, because `MasterItemId` is already set. It should do two extra things. It should name the auto-created shop category after the node's group (in the owner's language) instead of the raw master string, which ends literal "Men · Shirts and T-shirts" categories. And it should set `Category.NodeId` on that shop category when it has none. The second step also places the shopkeeper's own later hand-typed items in that category under the right tile. Families need no new table: a pack ladder is the products sharing a `MasterItemId`, and a clothes style or beauty shade group is the products sharing a `StyleName`.

### Worked example across the chain

A hardware-and-paint shop picks "Ball valve 20 mm" and "Wire 1.5 sq mm (90 m coil)" from the common list. The first master row has node `hardware/water/valves`. The second has `electrical/wires/house-wire` with `Attrs {"sqmm":1.5,"coilM":90}`. The shop gets two products linked by `MasterItemId`, plus shop categories "Valves" and "House wire" mapped to those nodes. On the bill, the menu shows a हार्डवेयर | पेंट | बिजली trade switch, and the valve sits under पानी, प्लंबिंग › Valves. In the store, the response now carries `nodeKey` on each item and a pre-counted `tree`, so the customer sees the same rail, tile and sq mm chip. Next month the platform moves valves under a new "Tanks, pumps & valves" tile. The shop's valve moves with it on both screens, and nobody touches the shop's data. If the owner had dragged the valve into a shop-only tile "Sintex & valves", their override wins, and the updates feed tells them the common list moved, so they can drop the override.

## Shops override presentation, the platform owns identity

The marketplace rule applies directly: shared content belongs to the shared record, and the seller changes only its own offer and its own shelf arrangement ([Amazon detail pages and offers](https://sellercentral.amazon.com/gp/help/external/help.html?itemID=51)). Presentation overrides go in one new shop-owned table, `shop_node_settings`. It holds `ShopId`, `NodeId`, `Hidden`, `HiddenOnline`, `Name`, `SortOrder` and `Icon`, is unique on (shop, node), and its migration calls the existing `EnableShopIsolation` helper. The helper's own comment says every new shop-owned table needs it, and 211 migrations already use it ([MigrationExtensions.cs](backend/src/GroceryKhata.Api/Persistence/MigrationExtensions.cs)). Shop-only tiles need no new table either. A shop `Category` whose `NodeId` points at a node, and whose name is not that node's name or alias, appears as an extra tile or chip under that node. If the name does match, it is just an alias and adds no tile.

| What | Shop may | Shop may not | Stored in |
|---|---|---|---|
| Item's place in the tree | Move one item to another node in its trade; map a whole shop category onto a node | Change the common-list item's node for other shops | `Product.NodeId`, `Category.NodeId` |
| Tree presentation | Hide a node everywhere or online only; rename it; reorder siblings; change its icon | Delete or re-parent a global node | `shop_node_settings` |
| Own shelves | Add shop-only tiles or chips under a global node ("Sintex tanks" under Water & plumbing) | Add a new department at level 1 in v1 (it would fork the tree) | Existing shop `categories` rows |
| Extra "also under" placements | — (v1) | Add extra nodes; these come only from the common list | `MasterItem.ExtraNodeIds` |
| Item identity | Rename the item locally; add its own photo | Edit the shared name, photo or attributes for everyone; send a correction through "suggest" instead | `Product` fields; `MasterSuggestion` |
| Tax | Accept or decline each GST/HSN change | Have tax change silently | Existing updates feed |
| Offer | Price, stock, sold-out today, online on/off | — | `Product` |

Two boundaries need explaining. Hiding a node hides its subtree **in menus only**: the items stay findable in search and sellable on the bill, so a shopkeeper cannot hide stock out of existence by accident. The bill menu ignores `HiddenOnline`, and the store applies both flags. GST and HSN keep their opt-in path, because a silent tax change would alter the shop's GST filing. Owner-only access, copied from `/categories`, is the default. Whether supervisors may rename nodes is undecided.

## Common-list changes flow down by link, not by name

Five kinds of platform change reach shops, and each needs its own rule. A **node move or re-parent** is followed live by every linked product without an override. Nothing is written to shop rows, and the existing updates feed gets a "moved" note only for shops that overrode the item. A **node merge or deactivation** sets `MergedIntoId`, and resolution follows it, the way `Categories.ResolveAsync` already follows merged shop categories. Overrides and `Category.NodeId` values pointing at the old node therefore keep working ([Categories.cs:83-111](backend/src/GroceryKhata.Api/Catalogue/Categories.cs)). A node key is **never deleted or reused**, following Shopify's archive-and-map rule ([Shopify/product-taxonomy](https://github.com/Shopify/product-taxonomy)). A **new common-list item** must reach existing shops' "new items" list. That means `SeedListsAsync` has to set `CreatedAt`, and a one-off fix should date the electrical and beauty rows that were added without it. **GST and HSN corrections** stay opt-in. **Item attribute changes**, such as a corrected sq mm value, flow live like the node.

The updates feed itself has to switch from names to links. `CompareAsync` should join on `Product.MasterItemId` and keep its name match only as the `LinkByNameAsync` back-fill for old unlinked items. The code's own comment admits that "items the shop renamed or made itself never match" ([MasterItems.cs:425-450, 502-521](backend/src/GroceryKhata.Api/Catalogue/MasterItems.cs)). Two smaller fixes belong in the same change. `AddTradeListAsync` should cover `ExtraTypes` as well as the primary `Type` ([MasterItems.cs:323-335](backend/src/GroceryKhata.Api/Catalogue/MasterItems.cs)). And bulk and master imports should apply category defaults, which today only single-item create does ([StockService.cs:146-151](backend/src/GroceryKhata.Api/Catalogue/StockService.cs)).

## The store shows a node only when it has something to sell

The bill, the supplier-order screen and the store should all draw on one tree endpoint, `GET /api/v1/catalogue/tree?trade=&context=bill|order|store`. Each context has its own item filter, and **a node appears only if it, or a node below it, holds at least one visible item**, with counts summed up the tree. That is the "no dead ends" rule from the menu reports, applied to customers. For the store, an item is visible when all of these hold:

- the product is active and priced above zero, which is today's rule;
- its effective node and every ancestor are active and not hidden by `Hidden` or `HiddenOnline`. This fixes today's bug where hidden categories still show online;
- the new per-item `Product.HideOnline` is off. There is no per-item online toggle today;
- the stock rule allows it, through a new shop setting `StoreShowOutOfStock`. It defaults to true, showing a greyed "sold out" item, which is today's behaviour; false hides items that are not `OnSale(today)`;
- for medical shops, Schedule X is never shown, and H/H1 items carry an Rx badge.

Jewellery pieces keep their own `JewelleryShowOnline` gate, and their node key comes from the adapter ([StoreEndpoints.cs:88-92, 125-140](backend/src/GroceryKhata.Api/Planner/StoreEndpoints.cs)). The store payload gains `nodeKey` on each item and a pre-filtered, counted `tree`. Each tile can then say "12 items · 9 in stock" with no second call, and the hard-coded `aisleOf` id ranges in the frontend can be deleted. Multi-trade shops get a trade switch rather than a merged rail. A product's trade is its effective node's trade, so the 25 item names that appear in more than one trade's list cause no conflict: each product links to one specific master row. The store DTO must therefore carry `ExtraTypes`, not just `Type`.

The real choice here is the publishing default. Vyapar makes shops add items to the online store one by one ([Vyapar blog](https://vyaparapp.in/blog/start-online-store-vyapar/)), and marketplaces publish only after quality checks ([Meesho QC](https://supplier.meesho.com/learning-hub/lessons/how-to-find-and-fix-qc-errors)). An opt-in default is safer, because an unpriced or mis-named item never leaks out. But it would empty every existing store overnight, and the app already uses price as the publish gate. The better path is to keep "priced = online", add the per-item and per-node hide switches, and offer opt-in as a shop setting for owners who want it. Medical compliance remains the one hard gate. The 2018 draft e-pharmacy rules were never notified, so the H/H1 prescription-upload rule should get a lawyer's check before it is enforced.

## Migration maps 82–85% of rows by their old category string

Order matters. **Map the common list first**, then let shop products inherit through `MasterItemId`. Because pick-time copied the master string into shop category names, most shop categories then map by alias too. A first pass over the CSVs estimates that **about 3,250–3,350 of 3,940 rows (82–85%) map from the category string alone**. About 550–650 rows need ordered keyword rules, and about 30–40 need a hand decision. These are regex heuristics, so expect ±10% on the rule-mapped buckets.

| Trade | Rows | By string | Needs rules or hands |
|---|---|---|---|
| Clothes | 204 | 160 split on " · "; 44 flat rows are departments | "Kids · Baby (0–2 years)" (12) split into Baby girl/boy by name or `for` |
| Electrical | 258 | 18 groups → 18 level-2 nodes under 9 rails, 100% | Parse sq mm, amps and watts into `Attrs` |
| Medical | 847 | 24 groups → 24 nodes under 9 departments, 100% | Concern overlaps via `LinkToId` |
| Paint | 337 | 13 categories → 6 departments | 7 "Other" rows by hand |
| Hardware | 319 | Most of 14 categories 1:1 or N:1 | **"Pipes and fittings" (71) → 7 water tiles**: keywords place 60; 11 misfits (Araldite, WD-40, wall putty, toilet seat cover, Tiscon) move by hand, plus about 5 more strays |
| Kirana | 958 | About 720 | About 240 in merged strings ("आटा, चावल, दाल" 99, "इंस्टेंट, नाश्ता" 54, "चाय, कॉफ़ी, दूध" 49…) split by name |
| Beauty | 1,017 | Most of 13 | "Skin care" (167) and "Bath, body…" (72) split into Face vs Body; 11 "Other"; `for` filled by category default plus men/baby words |

Starter-item trades (about 216 rows across 15 trades) get one-level trees built from their starter categories. Their old names ("Plumbing", "Interior", "Hinges") go into the node aliases, extending the 21 mappings `StarterGroups` already holds ([MasterItems.cs:261-275](backend/src/GroceryKhata.Api/Catalogue/MasterItems.cs)). On the shop side, a per-shop pass runs under that shop's own tenant context, like `LinkByNameAsync`. It first back-fills `MasterItemId` by name, then sets `Category.NodeId` wherever a shop category's normalised name matches a node name or alias in the shop's trades. **No product row gets a stored node.** Whatever stays unmapped surfaces in three places. Admins get an unmapped queue for common-list rows with a bulk "move to node". Admins also get a cross-shop view of unmapped shop category names, held in an **identity-free aggregate table** (trade, name, shop count, item count), so that RLS is never bypassed and no shop is named. Owners see a "not in the menu yet" picker on the Categories screen. Two numbers remain unknown until someone queries the live database: how many shop products lack a master link, and how many distinct shop category strings exist. That is the main risk to the 82–85% estimate holding at shop level.

## Build plan: relationship layer first, then the menus on top

The relationship layer comes to about **10–13 developer days plus 3–4 content days**. The extra day over the design note's 9–12 covers the link-based updates feed and the small flow fixes. These are estimates scaled from the earlier reports' sizing, not measurements. They exclude Hindi and Gujarati node names (no Gujarati source exists in the repo, and five CSVs have no Hindi names at all) and checking counter words with shopkeepers.

|---|---|---|---|
| 1 | `category_nodes` entity and migration (no RLS); `category-nodes.csv` per trade; only-add seeder; in-memory `TradeTrees` cache; `GET /catalogue/tree` replacing `/catalogue/aisles` | 1.5–2 d | One vocabulary exists |
| 2 | `MasterItem.NodeId / ExtraNodeIds / Attrs`; `node` and `attrs` CSV columns; seed and admin-import changes; `TradeAttributes` registry and validation; picker DTO gains `nodeKey` | 1.5–2 d | Picker groups by node |

| 5 | Flow fixes: `CompareAsync` by `MasterItemId`, a "moved" note for overridden items, `CreatedAt` on seeded rows and a back-date fix, `AddTradeListAsync` over `ExtraTypes`, category defaults on import | 1 d | Changes reach shops |
| 6 | `shop_node_settings` with `EnableShopIsolation`; hide, rename and order endpoints; per-context counts | 2 d | Shop overrides |
| 7 | Store: `nodeKey` and `tree` in the payload, `ExtraTypes`, visibility rules (`HideOnline`, `StoreShowOutOfStock`, Schedule X), deleting the `aisleOf` id ranges | 1 d | Customers see the same tree |
| 8 | Admin unmapped queue, identity-free unmapped-category aggregate, alias editing | 1.5–2 d | Long tail gets fixed |
| 9 | Tests: RLS isolation for `shop_node_settings`, resolution order, a master move followed or overridden, merged-node pointer, store visibility | 1 d | Safety net |

Steps 1, 2 and 4 can ship before any menu UI, and the picker immediately improves because it groups by node. Steps 6–7 should land together with the earlier plan's menu shell and bill steps, because they share the tree endpoint. After that the per-trade menus become data work on a shared base. Kirana goes first, as the reference. Then come clothes (already two levels), medical, beauty with the `for` switch, and hardware and paint with Water & plumbing as its own department. Electrical's 18 groups are now unblocked, because its master list exists. The jewellery adapter comes last. Three risks need naming. The node `Key` must be frozen once shipped. `Product.Category` must stay untouched to protect the report screens. And offline phones cache categories in `lib/catalogueSync.ts`, which this research did not examine, so the sync payload needs `nodeKey` added and checked before step 4 ships.

## Conclusion

The central insight is that the app does not need to move category data around. It needs to stop copying it. Every current failure traces back to one choice: categories travel as copied text, the update check matches by name, and the store rebuilds grouping from strings. One stable key on the common-list item, read live through the `MasterItemId` link the app already stores, makes the shop's list and the customer's store follow the platform's tree automatically. It also leaves shops a narrow, explicit set of overrides. The same choice turns migration from a data rewrite into an alias table: the old strings become aliases, not rows to rewrite.

The design also clarifies what the common list really is. It is not just a catalogue that shops pick items from. It is the **shared shelf map of each trade**, which the master items, the shop's own items and the customer store all point at. That opens two later moves at almost no extra cost. Nodes can carry ONDC domain and category codes, so a shop's items can be exported with the right attributes per category ([ONDC-RET-Specifications](https://github.com/ONDC-Official/ONDC-RET-Specifications)). And because shops' unmapped names and override patterns can be counted without identifying anyone, they become the evidence for growing each trade's tree from real counters rather than from guesswork.
